# 用于长期运行应用程序开发的工具框架设计

**来源**: https://www.anthropic.com/engineering/harness-design-long-running-apps

**摘要**: Anthropic 是一家人工智能安全与研究公司，致力于构建可靠、可解释且可控的 AI 系统。

---

本文由我们实验室团队成员 Prithvi Rajasekaran 撰写。

在过去的几个月里，我一直在研究两个相互关联的问题：让 Claude 生成高质量的前端设计，以及让它在无需人工干预的情况下构建完整的应用程序。这项工作源于我们早期在前端设计技能和长期运行编码代理工具框架方面的尝试。当时，我和同事们通过提示词工程（prompt engineering）和工具框架设计，成功将 Claude 的性能提升到了远超基准线的水平，但两者最终都遇到了瓶颈。

为了实现突破，我寻求了一些新颖的 AI 工程方法，这些方法适用于两个截然不同的领域：一个由主观品味定义，另一个由可验证的正确性和可用性定义。受生成对抗网络（GANs）的启发，我设计了一种包含生成器代理和评估器代理的多代理结构。要构建一个能够可靠且有品位地对输出进行评分的评估器，首先需要制定一套标准，将“这个设计好吗？”这类主观判断转化为具体的、可评分的术语。

随后，我将这些技术应用于长期运行的自主编码任务，并从我们早期的工具框架工作中汲取了两个经验：将构建过程分解为可处理的块，以及使用结构化制品（artifacts）在会话之间传递上下文。最终成果是一个三代理架构——规划器、生成器和评估器——它能够在长达数小时的自主编码会话中生成功能丰富的全栈应用程序。

## 为什么简单的实现方式效果不佳

我们此前已经证明，工具框架设计对长期运行的代理编码的有效性有着重大影响。在早期的实验中，我们使用初始化代理将产品规范分解为任务列表，并使用编码代理逐个功能地实现任务，然后通过制品传递上下文以跨会话保持状态。更广泛的开发者社区也得出了类似的见解，例如使用钩子（hooks）或脚本来保持代理处于持续迭代循环中的“Ralph Wiggum”方法。

但一些问题依然存在。对于更复杂的任务，代理往往会随着时间的推移而偏离轨道。在剖析这个问题时，我们观察到了代理执行此类任务时的两种常见失败模式。

首先是模型在处理长任务时，随着上下文窗口的填满，往往会失去连贯性（请参阅我们关于上下文工程的文章）。一些模型还会表现出“上下文焦虑”，即当它们接近自认为的上下文限制时，会过早地结束工作。上下文重置（完全清除上下文窗口并启动一个新的代理，结合携带前一个代理状态和后续步骤的结构化移交）解决了这两个问题。

这与压缩（compaction）不同，压缩是在原地总结对话的早期部分，以便同一个代理可以在缩短的历史记录上继续工作。虽然压缩保持了连续性，但它并没有给代理一个“干净的石板”，这意味着上下文焦虑仍然可能存在。重置提供了一个干净的石板，代价是移交制品必须包含足够的后续状态，以便下一个代理能够顺利接手工作。在我们早期的测试中，我们发现 Claude Sonnet 4.5 表现出的上下文焦虑非常强烈，仅靠压缩不足以实现强大的长任务性能，因此上下文重置对于工具框架设计至关重要。这解决了核心问题，但增加了编排复杂性、Token 开销以及每次运行的延迟。

第二个我们此前尚未解决的问题是自我评估。当被要求评估自己产生的工作时，代理往往会自信地赞美自己的工作——即使在人类观察者看来，其质量显然平庸。这个问题在设计等主观任务中尤为突出，因为在这些任务中，没有等同于可验证软件测试的二元检查。布局感觉是精致还是平庸是一个主观判断，而代理在给自己的工作评分时，往往会可靠地偏向正面。

然而，即使在有可验证结果的任务中，代理有时也会表现出糟糕的判断力，从而阻碍其完成任务。将执行工作的代理与评估工作的代理分离开来，被证明是解决这一问题的有力杠杆。这种分离本身并不能立即消除这种宽容度；评估器仍然是一个倾向于对 LLM 生成的输出持宽容态度的 LLM。但将一个独立的评估器调整为“持怀疑态度”要比让生成器批判自己的工作容易得多，而且一旦有了这种外部反馈，生成器就有了具体的迭代依据。

## 前端设计：让主观质量可评分

我首先在前端设计上进行了实验，因为自我评估问题在那里最为明显。在没有任何干预的情况下，Claude 通常倾向于选择安全、可预测的布局，这些布局在技术上是可行的，但在视觉上却平平无奇。

两个见解塑造了我为前端设计构建的工具框架。首先，虽然美学不能完全简化为一个分数——且个人品味总是因人而异——但可以通过编码设计原则和偏好的评分标准来加以改进。“这个设计美吗？”很难一致地回答，但“这是否遵循了我们良好的设计原则？”为 Claude 提供了一个具体的评分依据。其次，通过将前端生成与前端评分分离，我们可以创建一个驱动生成器产生更强输出的反馈循环。

考虑到这一点，我编写了四项评分标准，并在提示词中同时提供给了生成器和评估器代理：
- **设计质量**：设计是否感觉是一个连贯的整体，而不是部分的集合？在此项表现出色意味着色彩、排版、布局、图像和其他细节结合在一起，创造出独特的氛围和身份感。
- **原创性**：是否有自定义决策的证据，还是仅仅是模板布局、库默认设置和 AI 生成的模式？人类设计师应该能识别出刻意的创意选择。未经修改的库存组件——或 AI 生成的明显迹象（如白色卡片上的紫色渐变）——在此项上会失败。
- **工艺**：技术执行：排版层级、间距一致性、色彩和谐、对比度。这是一项能力检查，而非创意检查。大多数合理的实现默认都能做得很好；失败意味着基础不牢。
- **功能性**：独立于美学的可用性。用户能否理解界面功能、找到主要操作并完成任务而无需猜测？

我强调了设计质量和原创性，而非工艺和功能性。Claude 默认在工艺和功能性上已经得分很高，因为所需的技术能力往往是模型与生俱来的。但在设计和原创性上，Claude 往往只能产生平庸的作品。这些标准明确惩罚了高度通用的“AI 垃圾”模式，通过加大对设计和原创性的权重，促使模型在美学上进行更多的冒险。

我使用带有详细分数细分的少样本（few-shot）示例对评估器进行了校准。这确保了评估器的判断与我的偏好保持一致，并减少了迭代过程中的分数漂移。

我基于 Claude Agent SDK 构建了这个循环，这使得编排变得简单直接。生成器代理首先根据用户提示创建 HTML/CSS/JS 前端。我为评估器提供了 Playwright MCP，让它在对每个标准进行评分并撰写详细评论之前，能够直接与实时页面进行交互。在实践中，评估器会自行浏览页面，在生成评估结果之前进行截图并仔细研究实现细节。该反馈作为下一次迭代的输入流回生成器。我每生成一次运行 5 到 15 次迭代，每次迭代通常都会推动生成器朝着更独特的方向发展。
